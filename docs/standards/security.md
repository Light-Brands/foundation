# Security

- **Call `hasSession()` first in every server action behind the gate.** The public form action in `src/app/f/actions.ts` is the one exception: it serves `/contact` and every form under `/f/`, and the rule on public forms below covers it. `hasSession()` lives in `src/lib/auth/session.ts` and returns false when the PIN session is missing or expired. Return a plain message to the person when it is false, and change nothing. Why: a server action is a public endpoint, and the request gate does not protect it.
- **Send every redirect target through `safeNext`.** It lives in `src/lib/auth/gate.ts`, resolves the value against a fixed origin, and returns `/` for anything that leaves the site. Why: an unchecked `next` parameter turns the gate page into a link to anywhere.
- **Keep secrets in server-only modules that begin with `import "server-only"`.** `src/lib/env.ts` and `src/lib/auth/session.ts` are the pattern. Why: the build fails if client code imports them, so a secret cannot ship to a browser by accident.
- **Never give a secret a name that starts with `NEXT_PUBLIC_`.** Why: Next.js copies every such variable into the browser bundle.
- **Bind every local server to 127.0.0.1.** The `dev` and `start` scripts pass `-H 127.0.0.1`. Why: a server bound to every address is reachable by anyone on the same network.
- **Keep the sign-in limiter on `/api/gate`, and record each try before the PIN is compared.** `dbGateLimiter` in `src/lib/auth/limit.ts` keeps tries in `gate_attempts`. A client (one IPv4 address or one IPv6 /64) gets five tries in ten minutes, then waits ten minutes, doubling with each later lockout up to a day; that lockout falls only on that client. Once the whole site passes thirty tries in ten minutes it slows for fifteen minutes (doubling up to four hours): each network, an IPv4 /24 or an IPv6 /48, may then try once per thirty seconds, doubling up to a cap of five minutes. The site never closes, so a stranger guessing from many networks can make the owner wait at most that cap. Clients and networks are stored only as an HMAC under the session secret. Each try is read and written in one transaction under an advisory lock, so a burst at once is counted one by one, and a right PIN clears its client and gives the site its try back. A deploy with no database keeps the same limits in memory, per running copy. When the database cannot be reached, sign-in answers 503 and compares nothing. The PIN itself is compared as two SHA-256 digests with a constant-time loop (`pinMatches` in `src/lib/auth/pin-token.ts`). The owner's way in when sign-in is waiting needs no sign-in: `npm run auth:unlock` clears every row, against the hosted database when `FOUNDATION_DATABASE_URL` is set and the local one otherwise. Why: a six digit PIN falls to guessing without a limit that survives restarts, counts a burst exactly and cannot be spread across many addresses, and a limit a stranger can use to shut the owner out is a second attack.
- **Never run a shell command from a route or action.** No `exec`, `spawn` or `execSync` reachable from a request. Scripts in `scripts/` run only from npm scripts. `scripts/draft.ts` is the one place a process starts, from `npm run draft`. A test fails on any `child_process` import under `src/`. Why: a request that can start a process can take over the machine.
- **Build every public form on the helper under `/f/`, declared in the Key.** `submitPublicForm` in `src/lib/forms/public.ts` refuses a form the installed Key does not declare, only inserts (a new card, and a contact created or reused by email and never rewritten), caps every field and the whole body, discards a filled honeypot quietly, counts saves in the database per form and per client in one atomic step (`form_counts`, with `form_hits` as the log of saves), and records the source and the UTM values. `/contact` uses the same helper. A select with `options_from` only reads its app's table, and the save checks the value against that table again. No public upload in 1.0. Why: a form anyone can reach must not be able to change what the owner already saved, flood the Inbox, or open a second door with weaker locks.
- **Take inbound provider webhooks only at `/api/hooks/<connection>`, and verify before writing.** A connection declares `webhook: { verifier: verify.ts, secret_setting: NAME }` in `key/connections/<connection>.yaml`. `receiveWebhook` in `src/lib/hooks/receive.ts` answers 404 for a connection or verifier the Key does not declare, loads the verifier only from inside `key/connections/<connection>/`, reads the secret from the named setting (never a public or core one), verifies the signature on the raw body capped at 1 MB, and answers 401 with nothing written when it fails. The first record of an event id in `webhook_events` wins: a repeat answers 200 and does nothing, and `handle` runs only on the first. Records leave only through `npm run hooks:prune -- <days>`, 30 days at least. Why: a public address that writes before it checks the signature lets anyone forge a payment or a booking, and a replayed event must never act twice.
- **Send approved email only through `drainOutbox`, and only while email-sending is connected and the pause switch is off.** `src/lib/outbox/drain.ts` loads `key/connections/email-sending/send.ts` with the same confinement as a webhook verifier, reads the provider key from the setting the connection names, and never logs or stores its value. A read that errors, a missing sender, setting or `FOUNDATION_SECRET`, a `bounces` call that throws or returns something that is not a list, a bounce it cannot record and a recovery that throws each end the pass with nothing sent, and a row whose opt-out check errors stays approved. The pause switch is read again before each row, so a pause set during a pass stops the rows still to go. Every line it logs passes through `redact`, the sender's import failure and an unrecorded bounce among them. Why: one path that sends, with one set of checks, is a path that can be reasoned about.
- **Read a `FOUNDATION_SECRET` under 32 characters as unset, everywhere it is read.** `readEnv` in `src/lib/env.ts` then signs sessions and hashes visitors with the build secret, gives no fixed secret for opt-outs, and `src/lib/email-links.ts` neither makes nor reads an unsubscribe token under it. Why: a short secret can be guessed, and one rule in every place leaves no weak path.
- **Unsubscribe only at `/u/<token>`, where the token is the row's own HMAC.** The token is an outbox id and an HMAC of it under `FOUNDATION_SECRET` (`src/lib/email-links.ts`), so it never shows the address and cannot be made for another row. `handleUnsubscribe` in `src/lib/data/unsubscribe.ts` refuses a forged or oversized token before touching the database, answers a visit with a button and writes nothing, and on a post (the button or a mail app's one-click) records the opt-out for that marketing row's address, limited per row and per hour through `takeFormSlot`. Why: a link in every marketing email is a public address, and it must stop mail for exactly one person and nothing else.
- **Record each connection in `connections` with the name of the setting that holds its key, never the key.** `upsertConnection` in `src/lib/data/connections.ts` refuses a value that looks like a key, token, private key or password, and a setting name that starts with `NEXT_PUBLIC_`. Why: the table is shown on screens and read by every Settings job, so a key in it would travel wherever the data goes.
- **A setting name is checked heuristically.** `looksLikeSecret` in `src/lib/key-shape.ts` knows common key shapes and long mixed-case tokens, so an unusual key can still pass as a name. Read what you save. Why: no pattern can tell every key from every name, and the owner should know the check is a guard that can miss.
- **Call `looksLikeKey` from `src/lib/key-shape.ts` on free text an app saves, and refuse the save when it is true.** It runs the same key-shape test on the whole value and on each word in it, so a key pasted into a note or a description is caught before it lands in a table. Why: a key in an app's table is readable by everyone who can read that table, and travels with every export.
- **Accept the fixed-window edge of the public form limiter.** `takeFormSlot` in `src/lib/forms/limit.ts` counts saves per fixed window in `form_counts`, so a client can save up to twice its limit across a window boundary: the last moments of one window and the first of the next. This is an accepted trade-off. Why: one counter row settled by a single insert on conflict can never let two saves at once both take the last slot, and a sliding count over `form_hits` can, so a short burst at the edge is the price of a limit that cannot race.
- **Read the visitor's address for sign-in only from a header the host writes.** `clientAddress` in `src/lib/auth/limit.ts` reads `x-vercel-forwarded-for` on Vercel, which the platform writes itself. Anywhere else it reads only the header named in `FOUNDATION_CLIENT_IP_HEADER` (its last entry, the one your proxy added), and with none named every visitor shares one budget. To host elsewhere, put the app behind a proxy that sets or appends that header on every request, name it in `FOUNDATION_CLIENT_IP_HEADER`, and never expose the app's own port. The public form limiter still reads `clientKeyFromHeaders` (`x-vercel-forwarded-for`, then `x-real-ip`, then the first `x-forwarded-for` entry, else `local`); off Vercel those can be written by a visitor, so its per form budget is the limit that holds there. Why: a visitor who can write the header can pick a new address for every request and slip past a per client limit, and only the host in front of the app can be trusted to write it.
- **Treat the read-only run as the boundary for a check, and the Key checker as the early warning.** `runCheckSql` in `src/lib/checks/runner.ts` asks Postgres for the statement's verbose plan with its parameters bound, inside the read-only transaction, and refuses the check before it runs when the plan touches any relation outside the check's `reads` and its file's tables (its app, its installed `uses_apps` and the five core tables, never the outbox or another core table), or calls any function outside the checks' list. Postgres has already resolved views, CTEs, schema names and quoted names in that plan, so none of them hides a table. Then it runs the SQL as one parameterized statement wrapped in an outer select, inside a transaction opened read only, with a five second statement limit (enforced by the hosted database, since PGlite cannot interrupt itself), and rolls that transaction back whatever happens. `checkSqlProblems` in `src/lib/key/declarations.ts` reads comments, strings, quoted names and dollar quotes the way Postgres does before it scans, and refuses writing words, `into`, a second statement, dollar quoting and any function off its list, but it is a lint and never the only lock. Its reading of a plain string assumes `standard_conforming_strings = on`, so the runner sets it on for each check's transaction with `set local`. In the plan scan, a function Postgres quoted only because its name is a keyword (`"left"`, `"right"`) is read by that name, `POSITION(a IN b)` is read as `position`, and any other quoted name stays unknown and is refused. Why: a text check can always be fooled by some spelling, and a run that cannot write is safe whatever the text says.
- **Let the host's schedule in only with its secret.** `/api/cron/checks` is public only when the request carries `Authorization: Bearer <CRON_SECRET>`, a server-only setting of at least 16 characters, compared in constant time once the lengths match. With no secret set, the route refuses everyone. `isPublicRequest` in `src/lib/auth/gate.ts` lets nothing else through, and the route checks the secret again. Neither the route nor the owner's button takes a check, a period or a time from the request. Why: a scheduled route anyone can call is a way to run the business's routines from outside.
- **Make related writes one statement or one transaction.** When two rows have to agree, write them together with `begin` and `commit`, as the migration runner does. Why: a failure between two separate writes leaves records that disagree.
- **Never ask for the PIN, or any password, key or token, in a Claude conversation.** The member types secrets into their own terminal, for example with `npm run setup -- --pin-prompt`. Why: anything typed into a chat is stored by the chat.
- **Pin the host of an outside request and refuse redirects.** When code fetches a URL, check the host against the one expected and set `redirect: "error"`. Why: a redirect can send a trusted request to an address the owner never approved.
- **Check the session in the request gate and again at the action.** `src/proxy.ts` sends visitors without a session to `/gate`. The action's own check is still required. Why: the gate covers pages, and an action can be called without loading a page.
- **Write a card decision only through `decideCard`, once, from the session-checked Inbox action.** A decision records who and when and is never rewritten: the code checks, and a trigger on `inbox_items` refuses a second write. A card with `always_human` true is decided and closed by the owner role alone. Why: every draft and every action on a customer waits for a decision that can be trusted, and some decisions belong only to the owner.
